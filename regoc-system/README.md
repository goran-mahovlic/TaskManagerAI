# regoc-system — the REGOČ system kit

> Croatian version: [README.hr.md](README.hr.md) · Package: [../README.md](../README.md) ·
> Architecture: [../REGOC/ARHITEKTURA.en.md](../REGOC/ARHITEKTURA.en.md)

`regoc-system/` is the **system kit** (*komplet*) of TaskManagerAI: the orchestrator daemon
`RegocDaemon` with every module it imports, the helper agents, the tools the daemon starts, the
`SecurityValidator` hook for Claude Code and example settings. Without it TaskManagerAI is a board
(tasks, API, chat); with it the node also **runs** the work — it picks tasks, starts agents, checks
their results and closes tasks.

Since decision D3 (22 Oct 2026) the kit is **a folder of this package**, in the same repository and
the same commit as the board. There is no second repository and no lock file: what you cloned is what
gets installed, and `MANIFEST.sha256` in this folder proves that nothing was changed on the way.

## What is in the kit

| Path | What it is |
|---|---|
| `RegocDaemon.ts` | the orchestrator. Every second it reads the task database of the board, decides what may start (autonomy gate, concurrency cap, pause), starts agents (Claude CLI or another model), runs the independent critic over the result and closes or blocks the task |
| `MessageQueue.ts` | message queue between the daemon, agents and the user (SQLite `messages.db` in the kit folder) |
| `AgentDaemon.ts`, `AgentWorker.ts` | long-lived agent workers (team mode) and the worker that runs one agent turn |
| `CriticGate.ts`, `VerificationGate.ts`, `CompletionGuard.ts`, `MergeGate.ts` … | the gates a result passes before a task may be `completed` |
| `PauseControl.ts`, `ConcurrencySetting.ts`, `AutonomyThresholdSetting.ts` | the handbrake, the concurrency cap and the autonomy thresholds (see [Settings](#settings)) |
| `StaleCodeCheck.ts` | tells whether a running process still runs the code on disk |
| `lib/` | shared helpers: `spremiste-tajni.ts` (the only reader of the secret store), `okolina-sustava.ts` (machine identity from settings), `platforma.ts` (Linux/macOS differences) |
| `models/` | model abstraction (`ModelRouter`, `ModelInterface`) and `model-config.example.json` |
| `tools/` | tools the daemon starts: `modeli/` (Ollama and OpenRouter agent loops, consult), `orkestracija/`, `zadaci/checkpoint.ts`, `rag/lib/` (RAG over ChromaDB or pgvector), `hindsight/`, `servisi/` (`brana_brisanja.ts` — the deletion gate, `restart_kad_mirno.sh`) |
| `workflows/` | multi-step workflows (e.g. new project with a Nextcloud folder) |
| `zod/` | data schemas |
| `vanjsko/` | the few modules the daemon imports from outside `~/.claude/regoc`; `POVEZNICE.tsv` says where they are linked |
| `vanjsko/.claude/hooks/SecurityValidator.hook.ts` (+ `lib/`), `vanjsko/.claude/PAISECURITYSYSTEM/patterns.example.yaml`, `settings.json.primjer` | the Claude Code hook that blocks secret leaks and destructive commands for every agent |
| `config.primjer/`, `features.example.json`, `models/model-config.example.json` | example settings — copied only where nothing exists yet |
| `TAJNE.json` | names of every secret the kit's code reads, with description — **names only** ([Secrets](#secrets)) |
| `PREKIDACI.md` | every switch of `features.json` with its default and explanation (generated by the export) |
| `ULAZI.txt` | entry points; each one must build (`bun build`) |
| `instalacija.sh` | idempotent preparation after copying (prints `PROMIJENJENO` or `ISTO`) |
| `KOMPLET.json` | where the kit is installed (`odrediste`, relative to your home) — read by `install.sh` |
| `MANIFEST.sha256` | sha256 of every file of the kit |
| `package.json`, `bun.lock` | npm dependencies with exact versions |
| `tests/` | tests that run without any other part of the system |

## Installing (with `--komplet`)

From the package root, as the package README says (step 2):

```bash
bash scripts/install.sh --cvor <name> --profil upravitelj-cvora --baze --komplet
```

Step `K2.14-komplet` of `install.sh` then does, in this order (any failure stops the install with
exit code 5, and the services do not start):

1. **Checks this folder**: every file in `MANIFEST.sha256` exists with that sha256 and there is no
   file that is not in the manifest (only `node_modules/` may exist). A changed or damaged folder → exit 5.
2. **Copies** the folder to `~/.claude/regoc` (`odrediste` in `KOMPLET.json`, or `TM_KOMPLET_DIR`). Nothing is cloned or downloaded.
   If `~/.claude/regoc` exists and is not a kit (no `MANIFEST.sha256`), it is **not** overwritten → exit 5.
   If it is an installed kit with local changes in its files → exit 5 (a node is never patched in place).
3. Checks the copy against the manifest again.
4. `bun install --frozen-lockfile` in the kit.
5. `instalacija.sh --paket <package> --tm-home <TM_HOME>`: copies example settings where nothing
   exists (`config/`, `features.json`, `models/model-config.json`), links the modules from
   `POVEZNICE.tsv` into `~/.claude/…` (only where nothing exists), writes `~/.claude/settings.json`
   with the `SecurityValidator` hook (only if there is none) and links `credentials.env` to the
   package's secret store `$TM_HOME/config/credentials.env`. Everything it creates outside the kit is
   reported to `install.sh` and recorded in `$TM_HOME/instalirano.json`, so uninstalling removes it.
6. `bun build RegocDaemon.ts` — proof that the module graph resolves **before** any service starts.
7. Writes `TM_SUSTAV_DIR=~/.claude/regoc` and `TM_MODEL_CONFIG=…/models/model-config.json` into
   `$TM_HOME/config/instalacija.env`; the services `daemon` and `znanje` are installed (they exist
   only with `--komplet`).

Running `install.sh --komplet` again changes nothing when the folder did not change (`ISTO`).
`--suho` prints what would happen and changes nothing.

## Starting and stopping

The daemon runs as the service `daemon`, after the board (`taskmanager`). Both get their environment
from `scripts/s-okolinom.sh` (node settings, then secrets).

| | Linux (systemd user unit `regoc-daemon.service`) | macOS (LaunchDaemon `hr.regoc.daemon`) |
|---|---|---|
| state | `systemctl --user status regoc-daemon` | `sudo launchctl print system/hr.regoc.daemon` |
| start | `systemctl --user start regoc-daemon` | `sudo launchctl bootstrap system /Library/LaunchDaemons/hr.regoc.daemon.plist` |
| stop | `systemctl --user stop regoc-daemon` | `sudo launchctl bootout system/hr.regoc.daemon` |
| restart | `systemctl --user restart regoc-daemon` | `sudo launchctl kickstart -k system/hr.regoc.daemon` |
| after a crash | restarted after 5 s (`Restart=on-failure`) | restarted after 5 s (`KeepAlive` on failure) |

`templates/servis/sudoers.primjer` in the package allows exactly these `launchctl` commands without a
password, so the board can restart the service. To stop **work** without stopping the daemon use the
handbrake ([Settings](#settings)) — stopping the daemon leaves running agents without a supervisor.
While tasks are running, prefer `tools/servisi/restart_kad_mirno.sh`: it restarts when no task is
`in_progress`.

## Settings

The kit reads addresses and identity from settings, never from code.

| Setting | Where | Default without it |
|---|---|---|
| switches | `~/.claude/regoc/features.json` — every switch is listed in [PREKIDACI.md](PREKIDACI.md). The kit starts with `autonomyGate` and `ollamaClassifier` **off** (no usage meter and no Ollama on a new node) | `features.example.json` |
| **autonomy gate** | switch `autonomyGate`; thresholds on the board: Config → Concurrency cap and autonomy gates → Autonomy gates (`PUT /api/config/autonomy`): session 70 % (autonomy stops pulling work) / 85 % (caution, one agent) / 95 % (block), week 90 %. Needs the usage meter `session_usage.py` | off; thresholds 70/85/95/90 |
| **concurrency cap** | board: Config → Concurrency cap and autonomy gates → Concurrent agents (`PUT /api/config/concurrency`), stored in the board database with history; range 1–10. `REGOC_MAX_AGENT_CONCURRENT` is only the initial value | 3 |
| **handbrake** (pause) | board: the ⏸ Pause button (click again to resume; `/api/pause`). Global pause stops starting work and stops running agents; tasks keep their status. A single task can be paused too. State: `~/.claude/regoc/data/pause.state.json` | not paused |
| models | `~/.claude/regoc/models/model-config.json` (`apiKey` is always `env:NAME`) | `models/model-config.example.json` |
| Ollama | `OLLAMA_HOST` → `models/model-config.json` `providers.ollama.baseUrl` → `memory-config.json` | `http://127.0.0.1:11434` |
| ChromaDB | `CHROMA_HOST`/`CHROMA_PORT` → `memory-config.json` | `127.0.0.1:18765` |
| git identity, board URL, Telegram group and allowed user ids, memory bank | `~/.claude/regoc/config/okolina.json` | `REGOC <regoc@localhost>`, `http://localhost:17781`, none |
| gates, watchdogs, critic, workflows | `~/.claude/regoc/config/*.json` (from `config.primjer/`) | the example values |
| node settings (port, hosts, `NEXTCLOUD_URL`, `NEXTCLOUD_USER` …) | `$TM_HOME/config/postavke.env` — not secrets | — |

## Secrets

The kit reads secrets from **one** store: `~/.claude/regoc/credentials.env`, read only by
`lib/spremiste-tajni.ts`. With the package, `instalacija.sh` makes that a link to the package's store
`$TM_HOME/config/credentials.env` (mode 0600) — the same file the board writes when you enter a secret
on Config → Secrets. The reader understands the board's format (`NAME='value'`) and reads the file on
every use, so a newly entered secret works without a restart. Values are never printed, logged or
exported to other processes' environment.

`TAJNE.json` lists every secret name the kit's code reads. The list is **extracted from the code** by
the export (`izvuci_tajne.py`): a new secret in the code without a description stops the export. On a
node with the kit, the board shows all of these names on Config → Secrets, and the health check
(`bootcheck`, measurement M9) lists the ones that are still missing.

None of them is required for the daemon to run: agents through the Claude CLI need only the CLI login
(or `CLAUDE_CODE_OAUTH_TOKEN`, entered on the same page). Each other secret enables one provider or
feature:

| Name | What it is for | Without it | Read by |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | Anthropic API key for direct model calls from the daemon (provider anthropic in models/model-config.json). Agents run through the Claude CLI do NOT need it — they use the CLI login or the package's CLAUDE_CODE_OAUTH_TOKEN. | direct Anthropic API calls (classifier, in-process summaries) fall back to the next provider or are skipped; agents via the CLI keep working. | `models/ModelInterface.ts`, `models/ModelRouter.ts`, `models/model-config.example.json` |
| `DEEPSEEK_API_KEY` | DeepSeek API key (provider deepseek, Anthropic-compatible endpoint). | agents on deepseek:* models cannot run. | `models/model-config.example.json` |
| `GEMINI_API_KEY` | Google AI Studio API key. Used by the google provider (direct calls) and geminicli (agents through the `gemini` CLI — the daemon hands it to the agent process). | agents assigned to a geminicli:* model cannot run; the daemon skips them or moves them to another model. | `RegocDaemon.ts`, `models/ModelInterface.ts`, `models/ModelRouter.ts`, `models/model-config.example.json` |
| `GLM_API_KEY` | Z.ai GLM API key (provider glm, Anthropic-compatible endpoint). | agents on glm:* models cannot run. | `models/model-config.example.json` |
| `GOOGLE_API_KEY` | Older name of the same Google AI Studio key (fallback for GEMINI_API_KEY in the chain `env:GEMINI_API_KEY|GOOGLE_API_KEY`). Enter only one of the two names. | nothing if GEMINI_API_KEY is set; otherwise the same as without GEMINI_API_KEY. | `models/ModelInterface.ts`, `models/ModelRouter.ts`, `models/model-config.example.json` |
| `KIMI_API_KEY` | Moonshot Kimi API key (provider kimi, Anthropic-compatible endpoint): the daemon runs the Claude CLI against the Kimi model with it. | agents on kimi:* models cannot run. | `models/model-config.example.json` |
| `MINIMAX_API_KEY` | MiniMax API key (provider minimax, Anthropic-compatible endpoint). | agents on minimax:* models cannot run. | `models/model-config.example.json` |
| `NEXTCLOUD_PASSWORD` | Nextcloud password (or app password) for the “new project” workflow (workflows/CreateProjectWorkflow.ts: project folder and share). It also needs the settings NEXTCLOUD_URL and NEXTCLOUD_USER in $TM_HOME/config/postavke.env (not secrets). | projects are created without a Nextcloud folder; the workflow reports missing credentials. | `workflows/CreateProjectWorkflow.ts` |
| `OPENAI_API_KEY` | OpenAI API key for the openai provider (disabled by default in models/model-config.json). | the openai provider cannot be used; nothing else depends on it. | `models/ModelRouter.ts`, `models/model-config.example.json` |
| `OPENROUTER_API_KEY` | OpenRouter API key for agents on openrouter:* models (tool tools/modeli/openrouter-agent.ts). | agents on openrouter:* models cannot run. | `models/model-config.example.json`, `tools/modeli/openrouter-agent.ts` |
| `PGVECTOR_PASSWORD` | PostgreSQL/pgvector password for the kit's RAG when memory-config.json sets `rag.backend` to pgvector or dual (or REGOC_RAG_BACKEND). The package's local pgvector (install.sh --baze) has its own password TM_PGVECTOR_PASSWORD — this one is only for an external pgvector database. | the kit's RAG on pgvector does not work (agent knowledge search and store); not needed with ChromaDB (default). | `tools/rag/lib/rag-backend-factory.ts` |
| `QWEN_API_KEY` | Alibaba DashScope API key (provider qwen, Anthropic-compatible endpoint). | agents on qwen:* models cannot run. | `models/model-config.example.json` |

## Secrets after installation (step by step)

For the owner of the node, once `install.sh --komplet` has finished. The install and the agents never
enter secret values — only you do.

1. Open the board from a trusted network: `http://<node>:17781` (on the node itself, or over Tailscale).
2. In Telegram, send `/start` to the node's bot once (the board says which bot). The confirmation code
   goes only to your private chat.
3. Board → **Config → Secrets**. The list shows every secret of the package and of the kit; the kit's
   ones carry a description and, on hover, what does not work without them. All show “not entered”.
4. Type the value into the field of each secret you need (only the providers you actually use), then
   **Save**. The board sends an 8-digit code to your Telegram; enter it. The value goes into
   `$TM_HOME/config/credentials.env`; the page shows only “exists” and a fingerprint.
5. Check: `bash scripts/bootcheck.sh` — measurement **M9 secrets of the kit** must list only what you
   deliberately left out.
6. No restart is needed for secrets the kit reads from the store. If you entered `CLAUDE_CODE_OAUTH_TOKEN`
   or changed `NEXTCLOUD_URL`/`NEXTCLOUD_USER` in `postavke.env`, restart the daemon
   ([Starting and stopping](#starting-and-stopping)).

To change a secret, type the new value over it; to remove it, use **Delete** (also confirmed by a code).
On a node without Telegram, secrets are entered on the node: `bun scripts/tajna.ts postavi NAME`
(the value is read from the terminal, never from the command line).

## Upgrading

The kit is upgraded together with the package:

```bash
bash scripts/nadogradi.sh --git origin --grana main     # new package commit (board restarts)
bash scripts/install.sh --cvor <name> --profil upravitelj-cvora --baze --komplet
```

The second command checks the new `regoc-system/` against its manifest, removes from
`~/.claude/regoc` the files the new manifest no longer has, copies the new files and repeats steps
4–6. Your settings (`config/`, `features.json`, `models/model-config.json`), data (`data/`,
`messages.db`) and the secret store are not in the manifest and stay as they are. If you changed a kit
file by hand, the upgrade stops with exit 5 — a node is never patched in place.

## Uninstalling

```bash
bash scripts/deinstaliraj.sh              # services stop; the kit and data stay
bash scripts/deinstaliraj.sh --sve        # + $TM_HOME (a backup is made first)
bash scripts/deinstaliraj.sh --do-nule    # + everything the install created, from the manifest
```

`--do-nule` removes `~/.claude/regoc` and every link and file `instalacija.sh` created outside it
(listed in `$TM_HOME/instalirano.json`); things that existed before the install are not touched.

## Exporting the kit again (from the main system)

This folder is generated; fixes go to the main system first and come here with the next export.
On the main system:

```bash
bash ~/.claude/regoc/deploy/node-a-samostalnost/gradi_komplet.sh --javno [--izlaz DIR] [--bez-testa]
```

1. builds the module graph of every entry point (`bun build --metafile`) and collects the modules,
   the tools the daemon starts and their npm packages (test files of the main system are left out);
2. `sastavi_izvoz.py` lays out the tree: modules, `vanjsko/` + `POVEZNICE.tsv`, the hook,
   example settings without machine-specific values, `package.json` with exact versions,
   `TAJNE.json` (`izvuci_tajne.py`), `PREKIDACI.md`, this README;
3. `bun install --lockfile-only` writes `bun.lock`;
4. **gates** (`brane_izvoza.py`): private IPv4 addresses, tailnet addresses and names, `/home/<user>`
   and `/Users/<user>` paths, e-mail addresses, Telegram group and user ids, machine names, surname,
   memory bank names, everything from the main system's `config/okolina.json`, secret shapes, binary
   files, links pointing outside the tree — **a single hit stops the export**;
5. `MANIFEST.sha256`;
6. `bun install --frozen-lockfile` and `bun test` in a separate copy;
7. only then the folder `regoc-system/` of the package is replaced (default
   `~/app/TaskManager/TaskManagerAI/regoc-system`; `node_modules/` stays), checked with
   `sha256 -c`, gated again, and no manifest file may be ignored by the package's git.

The tool never commits or pushes: the export is committed on a branch of the package, the gates are
reviewed, and the owner pushes.

## Verifying

| Check | Command | Expected |
|---|---|---|
| folder = manifest | `cd regoc-system && sha256sum -c --quiet MANIFEST.sha256` (macOS: `shasum -a 256 -c --quiet MANIFEST.sha256`) | no output, exit 0 |
| kit tests | `cd regoc-system && bun install --frozen-lockfile && bun test` | `0 fail` |
| module graph | in the kit: `bun test` above (`tests/gradnja.test.ts` copies the kit into a temporary home, runs `instalacija.sh` and builds every entry point); installed: `bun build ~/.claude/regoc/RegocDaemon.ts --target=bun --outdir=/tmp/rd` | exit 0 |
| installed kit | `bash scripts/install.sh … --komplet --suho` | step `K2.14-komplet` reports “the same as regoc-system/” |
| node health | `bash scripts/bootcheck.sh` | `VERDIKT: PASS`; M9 lists missing secrets of the kit |

The package's own tests (`bun test` in the package root) do not run the kit's tests — the kit has its
own dependencies and runs them in this folder.

## What is never in the kit

API keys, tokens and passwords (every `apiKey` is an `env:NAME` reference; values live only in the
node's 0600 secret store), runtime data (`data/`, `messages.db`), node settings (`config/`,
`features.json`, `models/model-config.json`), logs, and any address, user id or e-mail of the machine
the kit was exported from. The export gates make sure of it; `tests/bez-nasih-vrijednosti.test.ts`
repeats the general gates here.
